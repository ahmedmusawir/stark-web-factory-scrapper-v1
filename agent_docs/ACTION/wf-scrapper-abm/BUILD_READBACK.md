## 3. Soft-block signals and local control proof

Existing product checks status 403/429 first but otherwise classifies success=False as generic failed; it does not map all explicit soft challenges to blocked. Library heuristics include 200 near-empty content and structural shells; generic Tier-2 Access Denied is not universally applied to HTTP 200. Thus reading an assumed flag or every library error as refusal would be incorrect.

The F-03 200 soft-denial body is specified with `<title>Access Denied</title>` and an explicit denial message, so detection is testable. Structural challenge-form/token or blocking challenge iframe is corroborated as document-preventing, not inferred from an unrelated CAPTCHA/script in an otherwise usable article. Record predicate, inspected source locator/header, status and available library reason. Historical wrapper used title/body checks (`...063951Z` wrapper inspect_dom); do not promote its broad string scan wholesale.

Plain empty body remains unsupported/empty_body; a near-empty/structural-only library heuristic is not proof of challenge and must be reported as unusable/incomplete failure rather than successful content or automatic site refusal. Ordinary 404/5xx/network/timeouts remain typed failures with no retry. An unrelated third-party analytics refusal is incidental evidence, not requested-document denial. A real document-preventing challenge stops regardless of HTTP 200. No challenge-solving, clicks/fills/submits. New detection precision remains unproven, with both positive and false-positive fixture cases required.
